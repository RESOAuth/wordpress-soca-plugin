# 0.3.0 directory release notes

The installable archive is `dist/simple-oauth-cimd-access-0.3.0.zip`; `dist/simple-oauth-cimd-access-0.3.0-source.zip` contains the repository tooling, tests and detailed documentation. Generate both with `python3 tools/build.py`, then verify `dist/SHA256SUMS`. The installable ZIP has one top-level `simple-oauth-cimd-access/` directory and includes `readme.txt`, the main plugin file, runtime source, `composer.json` and licenses. Detailed guides and test evidence remain in the repository and source archive, linked from the directory readme.

The plugin header and directory readme both use version/stable tag `0.3.0`, WordPress 6.8, PHP 8.1, and the `simple-oauth-cimd-access` text domain. The display name is **Simple OAuth CIMD Access**, so the expected directory slug matches the plugin folder. `Author: RESOAuth` and its GitHub organization URL are in the plugin header; the plugin URI points to this repository. The Composer package is `resoauth/simple-oauth-cimd-access`.

For an initial WordPress.org submission, upload the installable ZIP through the [plugin submission page](https://wordpress.org/plugins/developers/add/). WordPress.org assigns the directory slug during review. After approval, copy the installable folder's **contents** into the assigned SVN repository's `/trunk/` (the main PHP file must sit directly in trunk), copy trunk to `/tags/0.3.0/` with `svn cp`, and commit trunk and tag together. Confirm `Stable tag: 0.3.0` in both readmes. Follow the [WordPress.org SVN instructions](https://developer.wordpress.org/plugins/wordpress-org/how-to-use-subversion/).

The WordPress.org `Contributors` field is intentionally omitted until the submitting team supplies a verified WordPress.org username. The PHP `Author` field already identifies RESOAuth. Submit from the official RESOAuth WordPress.org account associated with `wordpress@resoauth.email`, as confirmed by the plugin owner; verify that account's profile email before upload. WordPress's [developer FAQ](https://developer.wordpress.org/plugins/wordpress-org/plugin-developer-faq/#how-do-i-submit-an-official-plugin) says official organization plugins must be submitted from the organization account. The directory listing links to the [default hosted gateway documentation](https://sag.resoauth.dev/hosted), its [privacy notice](https://sag.resoauth.dev/hosted/privacy-notice) and [terms of service](https://sag.resoauth.dev/hosted/terms-of-service). The separate [RESOAuth Dynamic CIMD](https://dynamic-cimd.resoauth.cloud/) service is linked and disclosed as the default metadata proxy for local development.

The `v0.1.0` GitHub release has already been published. Version `0.2.0` reset pre-release storage names and encryption context. Version `0.3.0` preserves 0.2.0 settings/keys but requires approved identity associations and a fresh candidate test before ordinary SSO. Follow the [migration procedure](GUIDE.md#upgrade-from-020-and-headless-setup) before rollout. The 0.3.0 artefacts are unreleased candidates until deliberately published. Against the [WordPress.org detailed plugin guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/), the plugin contains no payment, trial, license or quota gate for its included functionality. Its login rate limit is an abuse control. It does not download executable code or insert arbitrary PHP/JavaScript into the site. Its CIMD-based client registration and key rotation are the distinct capabilities described in the listing. Review the permanent display-name-derived slug before submission, as WordPress.org will not rename an approved slug.

The WordPress HTTP API sends outbound requests; its `http_api_curl` hook pins the resolved public address while checking the TLS hostname and certificate, preventing a DNS change between validation and connection. See [the current Plugin Check disposition](PLUGIN-CHECK.md) and [test evidence](TESTING.md) for the full review. The static scan is not a security audit.
